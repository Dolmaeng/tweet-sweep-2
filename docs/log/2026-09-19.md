## 연속 오류 자동 중지 폐지 (T41)

### 요청
- "세 번 연속 오류나면 자동 중지하는 로직 없애"
- "오류가 계속 일어나도 그 트윗은 스킵하고 다음 트윗을 계속 삭제해야 한다. 내가 자는 동안 코드가 모든 트윗을 빠짐없이 방문할 수 있도록"

### 고친 것
- `breaker.ts`의 `error` 분기에서 `consecutiveErrors >= 3 → halted`를 뺐다. 카운터는 진단용으로 남긴다
- 429 사다리·401/403·로그인·잠금은 그대로 멈춘다. 이것들은 "오류"가 아니라 계속하면 해로운 신호다

### 요청의 후반부 — "빠짐없이 방문"은 중지만 없앤다고 되지 않았다
두 루프 모두 건너뛴 글을 **다시 집지 않은 채 완료**로 끝나고 있었다.
- 아카이브: 오류 → `failed`, `nextPending`은 `pending`만 고른다. pending이 0이 되면 `decide`가 done을 준다. 밤새 돌면 실패한 글이 남은 채 "완료"가 된다
  → done 직전에 `requeueFailed()`를 부르고, 되살린 게 있으면 루프를 계속한다. `attempts` 상한(3)이 있어 유한하다
- 스윕: 오류 → `skip`에 넣고 다음 카드로. `skip`이 쌓이면 후보 없는 화면이 되고 `nextRecovery`가 done을 준다
  → `skip`이 비지 않았으면 최대 3라운드까지 `skip`·`seen`을 비우고 타임라인을 다시 훑는다. 끝내 남으면 완료 사유에 "N건은 오류로 건너뜀"을 적는다

### 남긴 것
- 무한 재시도는 만들지 않았다. 아카이브는 `attempts`, 스윕은 `SKIP_RETRY_ROUNDS`로 막는다
- 테스트 149개, 빌드 통과

## 200건쯤에서 page:unknown — 읽기 한도와 실패의 종류 (T42)

### 사용자 보고
- "항상 200개 삭제쯤 가까워지면 `error (page:unknown)`이 난다. 왜이러는걸까?"

### 추적
- `page:unknown` = `detectPageKind`가 article도 `error-detail`도 못 찾음 = X의 "Something went wrong" 화면. **글이 아니라 페이지가 안 열린 것**
- 200은 실측 DeleteTweet 한도(200/15분, ADR-0008)와 정확히 겹친다. 아카이브 모드는 1건 삭제 = 1페이지 로드라 읽기가 삭제와 1:1로 늘고, 0.3초 간격이면 1분 만에 창에 닿는다 — 그래서 "항상" 같은 지점

### 왜 아무것도 못 막았나 (두 겹)
1. `background.ts`가 `isGraphqlDelete`로 걸러 **삭제 응답만** 관측했다. 읽기 버킷은 감시망 밖
2. `scheduler.ts:54` `if (snap.remaining !== null && ...)` — 관측값이 없으면 **조건 전체가 건너뛰어진다**. 한도 감시가 없는 것과 같다

### 어제 바꾼 것과 겹쳐 더 나빠져 있었다
연속 오류 자동 중지를 뺀 뒤라, 200에서 막히면 멈추지 않고 남은 글을 간격마다 훑으며 전부 `failed`로 소진한다. `requeueFailed`의 `attempts` 상한(3)까지 태우면 멀쩡한 글이 영영 제외된다. **자고 일어나면 대부분 실패로 찍혀 있을 상태였다.**

### 고친 것
- `graphqlOperation()`으로 **모든 GraphQL 응답**의 예산을 관측. 연산별 버킷을 들고 있다가 **남은 비율이 가장 낮은 것**을 판단에 쓴다(`core/budget-buckets.ts`). 비율로 고르는 이유: 한도가 다른 버킷끼리 잔여 수치는 직접 비교할 수 없다
- `Signal`에 `page_unavailable` 추가. 종래엔 `dom_changed`였는데 그건 "셀렉터가 바뀌었다"는 뜻이라 원인이 전혀 다르다
- `markItem`·`upsertJobItem`에 `countAttempt`. 페이지 장애로 `attempts`를 깎지 않는다. 스윕은 `skip`에도 넣지 않는다
- 연속 페이지 장애마다 1분→2분→5분→15분 물러났다 계속한다(`core/backoff.ts`). 중지가 아니라 대기라 밤새 도는 목표는 유지
- 스윕: 새로고침해도 글 화면이 아니면 "더 지울 글이 없음"으로 읽지 않는다. 그대로 두면 예산이 바닥난 순간 작업이 조용히 "완료"로 끝났다

### 함정
- `pageBackoffMs`는 절대 0을 주지 않는다. 0이면 장애 중에 큐를 태운다
- 버킷은 `resetSec`이 지나거나 15분이 넘으면 버린다. 이미 리셋된 창의 값으로 판단하면 안 된다
- "첫 삭제 후 실측값으로 갱신됩니다"라는 안내가 안심시키는 거짓말이었다. 실제로는 그동안 한도 감시가 없다는 뜻이라 문구를 고쳤다
- 테스트 160개, 빌드 통과
