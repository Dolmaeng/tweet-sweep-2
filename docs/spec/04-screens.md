# 화면 설계 · 스토리보드

- 상태: 확정 · 2026-09-18 · 사용자 보고("'분석 → 삭제 실행'에는 필터링 옵션이 없다. UI가 헷갈린다")
- 결정은 ADR-0012. 1~3단계 모두 구현 완료(T38)

## 1. 무엇이 잘못됐나

사용자는 아카이브 경로로 삭제를 돌렸고, **미디어가 지워졌다**. 그 경로에는 미디어를 보존할 방법이 없다.

세 겹의 문제다.

### 1-1. 삭제 입구가 비대칭이다

홈에서 삭제로 가는 길은 둘인데, 하나만 삭제처럼 생겼다.

```
홈 ─ [아카이브 없이 삭제]  ← 버튼 이름이 삭제라고 말한다
   └ 계정 표 → [분석] → (리포트) → [삭제 실행]  ← 삭제 입구인 줄 모른다
```

`분석`은 리포트 이름인데 실제로는 **아카이브 기반 삭제의 유일한 입구**다. 사용자 표현 그대로 "분석은 사실상 아카이브 기반 삭제의 하위기능"이 돼 있다. 어느 화면에도 "지금 어느 모드인가"가 적혀 있지 않다.

### 1-2. 두 모드의 필터 어휘가 다르다

| | 아카이브 모드(`PlanRun`) | 스윕 모드(`SweepRun`) |
|---|---|---|
| 제목 | 대상 조건 | 트윗 청소기 필터 |
| 방향 | **포함** 기준(원글·답글·키워드 포함) + 보존이 섞임 | 전부 **보존**(제외) 기준 |
| 미디어 | **없음** | 2종(내가 올린 것 / 전부) |
| 멘션 | 없음 | 3종(모두·멘션만·멘션 제외) |
| 좋아요 | N개 이상 보존(정확한 수) | 1개 이상 보존 / 내가 좋아요한 글 |
| 기간·보존 ID | 있음 | 없음 |

같은 일을 하는 화면 둘이 서로 다른 말을 쓴다. 한쪽을 배우면 다른 쪽에서 틀린다.

### 1-3. 없는 조건이 조용히 없다

아카이브 모드에 미디어 항목이 **보이지도 않는다**. 사용자는 "체크를 안 했다"가 아니라 "체크할 칸이 없었다"는 걸 삭제가 끝난 뒤에 알게 된다. 되돌릴 수 없는 작업에서 가장 나쁜 실패 방식이다.

## 2. 설계 원칙

1. **모드는 입구에서 이름으로 고른다.** 삭제 경로 둘을 홈에 같은 무게로 나란히 둔다. `분석`은 리포트로 되돌린다.
2. **필터는 하나의 어휘, 하나의 방향.** 전부 "보존 = 지우지 않을 것" 기준으로 통일하고, 두 모드가 같은 컴포넌트를 쓴다.
3. **판정할 수 없는 조건은 숨기지 않고 잠근다.** 비활성 체크박스 + 왜 못 하는지 한 줄. 조건이 조용히 사라지는 경로를 없앤다 (헌장 P0).
4. **시작 직전에 무엇을 지울지 문장으로 되읽어준다.** 필터가 비어 있으면 "전부"라고 크게.

## 3. 화면 흐름 (제안)

```
                       ┌─ [아카이브 가져오기] ─→ 가져오기 ─→ 분석(리포트)
                       │
   홈(계정 목록) ──────┼─ 계정 행 [분석] ─→ 분석(리포트) ─┐
                       │                                   │
                       ├─ [아카이브로 삭제] ───────────────┴─→ 삭제 설정 ─→ 실행
                       │                                      (archive)
                       └─ [아카이브 없이 삭제] ──────────────→ 삭제 설정 ─→ 실행
                                                              (sweep)
```

핵심: **`삭제 설정` 화면은 하나의 뼈대**를 두 모드가 공유한다. 모드는 상단 배너와 잠긴 항목으로만 갈린다.

## 4. 와이어프레임

### 4-1. 홈

```
┌──────────────────────────────────────────────────────┐
│ 계정                                                  │
│                                                       │
│  @dolmaeng   12,430건   대상 11,208   2026-09-17      │
│              [분석]  [로컬 삭제]                      │
│                                                       │
│ ── 지우기 ────────────────────────────────────────    │
│  [아카이브로 삭제]        아카이브 zip의 목록대로.     │
│                           대상 수·기간·미리보기 있음.  │
│  [아카이브 없이 삭제]     로그인 세션의 타임라인을     │
│                           위에서부터. 목록 없음.       │
│                                                       │
│  [아카이브 가져오기]  [설정]                          │
└──────────────────────────────────────────────────────┘
```

- 삭제 버튼 둘이 같은 자리, 같은 무게. 한 줄 설명으로 차이를 말한다.
- `분석`은 계정 행에만 남는다. 삭제 입구가 아니다.
- 아카이브가 없으면 `[아카이브로 삭제]`는 비활성 + "먼저 아카이브를 가져오세요".

## 5. 필터 능력 매트릭스

이 표가 잠금 UI의 근거다. 못 하는 건 못 한다고 화면에 쓴다.

| 보존 조건 | 아카이브 | 스윕 | 비고 |
|---|---|---|---|
| 멘션 구분 | ✅ `inReplyToId`·본문 `@` | ✅ 답글 카드·본문 `@` | |
| 미디어가 있는 글 | ✅ `hasMedia` | ✅ `hasMedia` | **아카이브에 신규 추가** |
| 내가 올린 미디어만 | 🔒 인용 여부 미보존 | ✅ `ownMedia` | 아카이브는 구분 불가 |
| 좋아요 N개 이상 | ✅ 정확한 수 | ⚠️ 1개 이상만 | 스윕은 숫자 대신 고정 문구 |
| 리포스트 N개 이상 | ✅ 정확한 수 | ⚠️ 1개 이상만 | |
| 북마크 1개 이상 | 🔒 없음 | ⚠️ 라이브 미검증 | T35 검증 대기 항목 |
| 내가 좋아요한 글 | 🔒 `like.js` 미독해 | ✅ `unlike` 버튼 | 아카이브에서 읽으려면 별도 작업 |
| 내가 북마크한 글 | 🔒 아카이브에 없음 | ✅ `removeBookmark` | |
| 내가 리트윗한 글 | ✅ `kind==='retweet'` (v1 기본 제외) | ✅ `unretweet` | |
| 키워드 제외 | ✅ | ✅ | |
| 정규식 | ✅ | 🔒 | 스윕은 본문이 잘릴 수 있음 |
| 기간 | ✅ 정확 | 🔒 | 스윕도 `<time>`은 읽지만 위에서부터 훑는 구조라 범위 지정이 무의미 |
| 원글/답글 종류 | ✅ | 🔒 답글만 판정 | |
| 보존할 글 ID | ✅ | 🔒 | |

✅ 사용 가능 · ⚠️ 정밀도 낮음(문구로 밝힘) · 🔒 비활성 + 이유 표시

## 6. 데이터 모델

`core/filters.ts`의 `FilterSpec`(아카이브)과 `core/sweep-filter.ts`의 `SweepFilter`(스윕)를 **`core/keep-filter.ts` 하나로 합친다**.

구현된 모양:

```ts
export interface KeepFilter {
  // §1 대상 범위 — 포함 방향
  mention: MentionMode;
  kinds: PostKind[];
  from: string; to: string;        // 'YYYY-MM-DD', '' = 제한 없음
  includeKeyword: string;
  includeRegex: string;
  // §2 보존 — 제외 방향
  keep: KeepFlag[];
  keepMinLikes: string;            // 입력 원문. 파싱은 판정 직전 한 번
  keepMinRetweets: string;
  keepIds: string;
  excludeKeywords: string;
}

/** UI 잠금과 판정 경계가 같은 표를 본다 */
export const CAPABLE_FLAGS: Record<Mode, KeepFlag[]>;
export const CAPABLE_FIELDS: Record<Mode, KeepField[]>;
```

숫자·날짜·id 목록까지 문자열로 들고 있는 이유: 이 값이 **저장값이자 폼 상태**다. 두 표현을 따로 두면 "화면에 보이는 값"과 "판정에 쓰이는 값"이 갈라질 자리가 또 생긴다.

판정 함수는 모드별로 둘(`isTargetArchive` / `isKeptSweep`)이되 **같은 `KeepFilter`를 읽는다**. 한쪽이 무시하는 필드는 `CAPABLE_*`에 없고, UI는 그 표로 잠근다. 표가 하나이므로 화면과 로직이 어긋날 수 없다.

방향을 하나로 통일하지 않고 섹션으로 가른 이유: "이 말이 든 글만 지우기"(포함)가 실제로 쓸모 있어 버릴 수 없다. 섹션 제목이 방향을 말하면 섞이지 않는다.

### 저장값 마이그레이션

- `settings.sweepFilter`: 기존 `SweepFilter` → `KeepFilter`. `coerceKeepFilter()`가 구버전 키(`exclude[]`·`keywords`)를 읽어 옮긴다. 플래그 이름이 같아 변환이 단순하다. 못 읽으면 **필터 없음이 아니라 오류**로 처리한다(d4a46ab에서 넣은 가드와 같은 이유).
- `settings.archiveFilter`: 신규. 아카이브 필터도 이제 저장한다 — 매번 미디어 보존을 다시 체크하게 두면 같은 사고가 다시 난다.
- `job.filterSpec`: `unknown`으로 저장돼 있어 스키마 변경에 안전하다. 이어서 하기(resume)는 화면의 현재 필터를 쓰므로 영향 없음.

## 7. 단계 (완료)

| 단계 | 내용 | 커밋 |
|---|---|---|
| **1. 안전** | 아카이브 모드에 미디어 보존 조건 추가 + 두 화면에 모드 배너 · `분석`의 버튼을 `이 아카이브로 삭제`로 | e14da15 |
| **2. 통합** | `keep-filter.ts`로 모델 합치고 공유 컴포넌트 · 능력 매트릭스 잠금 UI · 되읽기 박스 | 8b62650 |
| **3. 입구** | 홈에 삭제 버튼 둘 나란히 · `분석`을 리포트로 · 계정 선택 | 04060d9 |

1단계만으로도 이번 사고는 재발하지 않는다. 2단계가 "헷갈린다"의 본체였다.

## 8. 열린 질문

- 아카이브 `like.js`를 읽어 "내가 좋아요한 글"을 아카이브 모드에도 열어줄지 — 별도 작업(가져오기 파서 변경). 지금은 잠금으로 둔다
- 스윕에 기간 조건을 넣을지 — 위에서부터 훑는 구조상 "이 날짜보다 오래된 것만"은 가능하다. 필요하면 별도 결정
