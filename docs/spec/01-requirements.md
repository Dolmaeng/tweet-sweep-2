# 요구사항 명세 (SRS)

- 상태: v0.4 · 2026-09-17 · FR-11a 실시간 진행 표시 추가. 적응형 페이싱(ADR-0007) 반영. 전작 `tweet-sweep` SRS v0.3을 세션 방식으로 개정
- 표기: **[확정]** / **[미정→Qn]**(§10) / **[제안]**
- 상위 문서 `00-constitution.md` · 결정 근거 `../adr/`

## 1. 배경·목표
- 개인 X 계정(최대 3개)의 과거 게시물을 비용 0원으로, 계정 잠금 위험을 최소화하며 삭제. 속도보다 안전
- 부수 목표(우선순위): ① 안전 ② 에이전틱 코딩·오케스트레이션 학습 ③ LLM 내부 원리 ④ 웹/프론트/CS 기본기(확장 API·DOM·TS·IndexedDB) ⑤ 확장 가능 구조 ⑥ 블로그 소재
- 성공 기준: 대상 100% 삭제 · 계정 영구 정지 0회(일시 잠금은 복구 절차로 대응) · 비용 0원 · 다른 Windows PC에서 clone 후 재현

## 2. 범위
### 포함
- Chrome 확장(MV3). 실행 단위 = 현재 로그인 계정 1개 + 그 계정의 아카이브 1개 **[확정]**
- 아카이브 가져오기 → 인벤토리(IndexedDB) → `analyze` 보고서 → 필터 → `plan`(dry-run) → `run`(작업 탭에서 삭제) → 감사 로그·내보내기
- 대상 유형 v1: 원글, 답글, 미디어 포함 게시물 **[확정]**
- 대시보드 페이지(진행률·설정·로그) = 오케스트레이터 **[확정, ADR-0004]**
### 제외 (v1) — 확장 지점으로 예약
- 리포스트 취소 · 좋아요 취소 · 북마크 · DM · 팔로우 정리 · 아카이브 이후 게시물 보충 · 백그라운드(대시보드 닫힘) 실행 · 스토어 배포

## 3. 환경·전제
- Windows 11 Home · Chrome 152 · Edge 153 · Node.js LTS 설치 필요(WXT 빌드, M1 첫 작업) **[확정]**
- 계정 규모 합계 1만~3만 건. 계정별 아카이브 zip 보유. 사용자가 해당 계정으로 Chrome에 로그인한 상태에서 실행
- X 웹 클라이언트 삭제 한도는 비공개지만 응답 헤더 `x-rate-limit-*`로 예산이 드러남 → 실측해 속도를 정함. 미관측 시 공식 API와 같은 50/15min 가정

## 6. 안전 정책 (적응형 페이싱, ADR-0007)
- 원칙: 속도는 추측하지 않고 X가 응답 헤더로 알려주는 예산에서 정한다. DeleteTweet 응답의 `x-rate-limit-limit`(L)·`-remaining`(R)·`-reset`(창 W, 보통 900s)을 webRequest로 관측
- 기본 간격 = W ÷ (u × L). u = 프리셋의 예산 사용률. 미관측 시 L=50, W=900 가정
- 지터: 로그노멀 배수(중앙값 1.0, σ 0.35) → 오른쪽 꼬리가 긴 사람형 분포. 균등·정규분포를 하한으로 자를 때 생기는 하한 봉우리 없음. 4% 확률로 20~40초 휴식(사용자 조정 2026-09-17, 원래 2~8분). 세션 휴식(60~120분마다 10~30분)은 미구현·보류
- 잔여 예산 감시: R < (1−u)×L 이면(사용자 수동 활동 포함) reset까지 대기 → 429를 맞기 전에 멈춤

| 프리셋 | u | 플로어 | 미관측(L=50) 간격 | L=100 간격 | 일일(14h, L=50) |
|---|---|---|---|---|---|
| `cautious` | 0.3 | 30s | ≈60s | ≈30s | ≈840 |
| `normal` | 0.5 | 18s | ≈36s | ≈18s | ≈1,400 |
| `brisk`(기본) | 0.7 | 5s(ADR-0008) | ≈26s | ≈13s | ≈1,960 |

- 실측(2026-09-17): 웹 클라이언트 DeleteTweet L=200/15min → brisk 간격 ≈6.4s, 10시간 ≈5,600건. 하드 최소 5s·일 절대 상한 8,000(ADR-0008)

- 일일 상한: 고정값 없음. u × L × 활동 창 수로 도출, ±15% 일별 무작위. 절대 상한 8,000/일(헤더 오독 대비, ADR-0008)
- 워밍업: 첫 100건 u=0.3(헤더 측정 겸용) → 다음 200건 동안 프리셋 u까지 선형 상승
- 활동 시간대 기본 09:00~23:00. 시작·종료 매일 ±45분 무작위. 주 1회 무작위 휴무는 옵션(기본 꺼짐)
- 차단 사다리: 429 1회 → reset + 5~15분 대기, u −0.1 · 같은 날 2회 → 2~4h 정지, u −0.1 · 3회 → 다음 날까지 정지 · 401/403·로그인·잠금 페이지 → 완전 정지, 사람 확인 · 연속 오류 3회 → 정지
- 하드 제약(코드 고정): 간격 ≥5s · u ≤0.7 · 동시 요청 1 · 일 ≤8,000 · 헤더 미관측이면 u=0.3 고정 (ADR-0008)
- 하지 않는 것(ADR-0007): User-Agent·IP·프록시 변경, 주기적 재로그인, 자동 좋아요·게시 위장, 외부 전송 로그
- 실행 전 체크: 로그인 상태, `twid` 일치, 활동 시간대, 잔여 예산

## 7. 제약·가정
- X 웹 클라이언트는 예고 없이 바뀜(DOM·문구·GraphQL 식별자) → 실행기 2종, 설정 오버라이드, 계약 테스트
- 백그라운드 탭 타이머 제한 → 작업 탭은 별도 창 또는 활성 유지. 절전 모드 시 중단
- 합성 클릭 `isTrusted=false`를 X가 검사하기 시작하면 UI 실행기 파손 → `chrome.debugger` 입력 이벤트 대체안
- 아카이브 이후 게시물은 v1 범위 밖
