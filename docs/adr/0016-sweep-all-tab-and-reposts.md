# ADR-0016: 스윕은 "전체" 탭에서 훑고, 리포스트는 재게시 취소로 치운다

- 상태: 확정 · 2026-09-23 · 사용자 보고("이상하게 이 머신은 'Replies' 탭을 활성화해서 삭제하는거같아. 그러면 답멘만 지우는거야")
- ADR-0009이 정한 스캔 페이지(`/<handle>/with_replies`)를 바꾸고, FR-18의 "리포스트 제외"를 뒤집는다

## X가 프로필 탭을 바꿨다

ADR-0009을 쓴 2026-09-17에는 `/<handle>/with_replies`가 **원글과 답글이 함께 나오는** 타임라인이었다. 그래서 탭 하나만 훑으면 됐다.

2026-09-23 라이브 확인(`x.com/gujik_man`, ko) 결과 지금은 다르다. 프로필 탭 줄은 `[role="tab"]` 앵커 넷이다.

| 탭 | href | 내용 |
|---|---|---|
| 게시물 / **전체** | `/<handle>` · `/<handle>/all` | 맨 왼쪽. `aria-haspopup="menu"`로 드롭다운을 연다 |
| 답글 | `/<handle>/with_replies` | **답글만** |
| 재게시 | `/<handle>/reposts` | 리포스트만 |
| 미디어 | `/<handle>/media` | 미디어가 붙은 글만 |

맨 왼쪽 드롭다운 항목은 href 없는 `div[role="menuitem"]` 넷이다: **전체 · 게시물 · 하이라이트 · 정렬 기준**. "정렬 기준"은 하위 메뉴 `[role="menuitemradio"]` 둘을 연다 — "최신 순서"(기본 체크) · "인기".

즉 `with_replies`는 더 이상 "원글+답글"이 아니라 **답글 탭**이다. 스윕은 그 탭을 열고 있었으므로 답글만 지우고 있었다. 사용자가 본 그대로다.

## 결정

### 1. 기본 스캔 페이지는 "전체" 탭이다

"전체"를 고르면 주소가 `/<handle>/all`이 된다. **이 주소로 직접 들어가도 전체가 선택된 채 열린다**(확인함). 그래서 평소에는 URL 한 번이면 끝나고, 메뉴를 누를 일이 없다.

그래도 누르는 경로(`executors/profile-tabs.ts`)를 함께 둔다. X가 그 주소를 안 받아주면 드롭다운을 열어 "전체"를 누른다. 판정은 선택된 탭의 href(`/all`로 끝나는가)로 한다.

**주소가 그 탭이 아니면 실행을 멈춘다.** 탭 줄을 못 읽는 것과 엉뚱한 타임라인에 서 있는 것은 다르다. 후자를 그냥 진행하면 사용자가 지우라고 하지 않은 곳에서 지운다.

### 2. 답글만 노리는 필터일 때만 답글 탭

`sweepTabOf(filter)`: 멘션 모드가 `only`("멘션만 포함")면 `with_replies`, 아니면 `all`. '멘션 제외'는 답글이 **아닌** 글을 지우겠다는 뜻이므로 전체 탭이 맞다.

답글만 지울 때 전체 탭을 훑으면 대부분을 보존 판정으로 버리게 된다. 답글만 모인 타임라인이 훨씬 빠르다.

### 3. 정렬은 실행당 한 번 "최신 순서"로 맞춘다

"인기"로 돼 있으면 타임라인이 시간순이 아니라 최신부터 지울 수 없다. 실행 시작 때 한 번만 확인하고, 이미 최신순이면 아무것도 누르지 않는다. 메뉴를 여닫는 동작이라 삭제 루프 안에서 반복하지 않는다. 못 맞춰도 실행은 계속한다 — 맞추면 좋은 것이지 막을 일이 아니다.

### 4. 내가 누른 리포스트는 재게시 취소로 치운다

FR-18의 "리포스트 제외"를 뒤집는다. 전체 탭에 리포스트가 같이 나오는데 건너뛰면, 사용자가 "다 지웠다"고 생각한 자리에 리포스트만 남는다.

리포스트는 **삭제가 아니다.** 경로가 완전히 다르다.

- 카드의 `[data-testid="unretweet"]` → 열린 메뉴의 `[data-testid="unretweetConfirm"]`("재게시 취소"). 확인 시트는 없다
- **caret 메뉴를 절대 열지 않는다.** 리포스트 카드의 caret은 원작성자에 대한 메뉴(언팔로우·차단·신고)다. 2026-09-17에 그 메뉴가 열려 연속 오류로 정지한 적이 있다
- 카드는 **링크가 일치하는 것만** 쓴다(`findCardArticle`). 삭제 쪽의 "화면에 카드가 하나뿐이면 허용" 완화를 여기 두면, 타임라인에서 옆 사람의 재게시를 취소하는 길이 된다

안전 판정도 바뀐다. 리포스트 카드의 permalink handle은 **원작성자**라 기존 handle 비교가 통하지 않는다. 대신 `unretweet` 버튼의 존재(`retweeted`)를 증거로 쓴다. 그 버튼이 있다는 것은 내가 눌렀다는 뜻이고, 재게시 취소는 내 행동만 되돌린다. 증거가 없으면 손대지 않는다. 리포스트가 아닌 카드는 종래대로 handle이 나와 같아야 한다.

보존 장치는 이미 있다 — 보존 필터의 "내가 리포스트한 글"을 켜면 리포스트가 다시 대상에서 빠진다.

## 남는 것

- 미디어·리포스트를 위해 별도 탭(`/media`·`/reposts`)에 갈 일은 없다. 전체 탭에 다 나온다
- 리포스트의 `postId`는 **원글의 id**다. "최신부터"가 리포스트에 대해서는 내가 누른 시각이 아니라 원글 작성 시각 기준이 된다. 순서만의 문제이고 결국 다 치운다
- 아카이브 모드는 그대로다. zip 목록에는 원글과 답글만 들어간다
- 라이브 검증 대기: 전체 탭에서 실제 삭제·재게시 취소가 연속으로 도는지, 탭이 풀리지 않는지

## 대안

| 대안 | 내용 | 판단 |
|---|---|---|
| 탭마다 따로 돌기 | 전체·미디어·재게시를 순서대로 | 기각: 전체 탭에 다 나온다. 탭을 오가면 상태와 스크롤 위치가 늘어난다 |
| 드롭다운만 쓰고 URL은 안 쓰기 | 항상 눌러서 고르기 | 기각: 주소로 되는 것을 매번 두 번 누를 이유가 없다. 클릭은 대비책으로 남긴다 |
| 리포스트도 caret 메뉴로 | 삭제와 같은 경로 | 기각: 그 메뉴는 원작성자 메뉴다. 차단·신고가 거기 있다 |
| 리포스트는 계속 제외 | FR-18 유지 | 기각: 사용자가 명시적으로 요구했다. 보존 필터에 이미 되돌릴 스위치가 있다 |
| 정렬을 매번 확인 | 루프마다 | 기각: 메뉴를 여닫는 동작이라 삭제 루프 안에서 반복하면 사고가 는다 |
