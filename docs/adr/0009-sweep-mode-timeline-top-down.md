# ADR-0009: 스윕 모드 — 아카이브 없이 타임라인 맨 위부터 삭제

- 상태: 확정 · 2026-09-17 · 사용자 요청(다른 계정 전체 삭제, 필터 없음)

## 맥락
- 아카이브 zip은 신청 후 받기까지 며칠 걸린다. 두 번째 계정을 지금 정리하려면 목록 없이 시작할 방법이 필요
- 사용자 용도 확정: **다른 계정 전체 삭제**. 기간·키워드 필터 불필요(전부 삭제)
- 제약 조사: X는 프로필 타임라인을 최근 약 3,200건까지만 돌려준다(API v2 명시). 웹 스크롤은 그보다 못 미치는 경우가 많고 기기·날짜에 따라 달라진다
  - 출처: devcommunity.x.com "Tweet Limit at 3200", 웹 스크롤 한도 보고 다수

## 결정
- **목록을 만들지 않는다.** 타임라인 맨 위의 대상 글을 그 자리에서 삭제하고, 다음 글이 올라오면 반복한다
- 스캔 페이지는 `/<handle>/with_replies` 하나. 원글과 답글이 같은 타임라인에 나오므로 탭을 오갈 필요가 없다
- 대상 계정은 **입력받지 않는다.** 왼쪽 내비의 프로필 링크(`AppTabBar_Profile_Link`)에서 로그인된 handle을 읽어 그 계정만 쓴다
- 후보 판정: article의 타임스탬프 permalink `/<handle>/status/<id>`에서 handle이 내 것이고, 리포스트가 아닌 글. 고정글은 **후보 중 마지막 순위**(다른 후보가 없을 때만 선택)
- 삭제는 기존 `ui-click` 실행기(`deletePost`)를 그대로 쓴다. 타임라인 카드에도 `article[data-testid="tweet"]` · 카드 안 caret · 확인 시트가 동일하게 있다
- 페이싱·회로차단·활동 시간대·예산 감시는 기존 코어를 그대로 재사용
- 삭제 직전 카드에서 본문·작성시각을 읽어 감사 로그에 남긴다(FR-12 스냅샷의 축소판)

## 이유
- **3,200건 벽을 우회한다.** 항상 맨 위 20~30건만 보므로 깊은 페이지네이션이 없다. 한 건 지울 때마다 그만큼 오래된 글이 위로 올라와, 결과적으로 전체 이력을 훑는다
- **요청과 시간이 준다.** 아카이브 방식은 글마다 상세 페이지를 연다(내비게이션 1회 + 렌더 대기). 스윕은 같은 페이지에서 메뉴만 연다
- **오삭제 경로가 없다.** 대상 계정을 세션에서 읽으므로 아카이브·로그인 불일치 사고(FR-03이 막던 것)가 구조적으로 발생하지 않는다
- 최신순 기본값(FR-10a)과 맞물린다. 타임라인은 최신이 위이므로 추가 정렬이 필요 없다

## 대안
| 대안 | 내용 | 판단 |
|---|---|---|
| 전체 스캔 후 기존 파이프라인 | 끝까지 스크롤해 목록을 만들고 계획·필터·dry-run 재사용 | 기각: 3,200건 벽에 막혀 2만 건대 계정 대부분을 못 봄. 스크롤 자체가 수천 요청 |
| 검색 `from:` 기간 분할 | 기간을 잘라 검색으로 수집해 벽 우회 | 기각: 검색 인덱스 누락 가능, 요청 수가 크게 늘어 탐지 위험 상승 |
| `graphql-replay`로 UserTweets 재전송 | 커서 페이지네이션 직접 구동 | 보류: ADR-0005의 식별자 회전·헤더 누락 위험. 스윕은 UI만으로 충분 |

## 위험·한계
- 목록이 없으므로 **전체 건수를 미리 알 수 없다.** 카운터는 `deleted N`만 표시(FR-11a의 M 생략). 프로필 헤더 수치는 축약 표기라 신뢰하지 않는다
- dry-run이 없다. 되돌릴 수 없는 작업이므로 실행 전 **handle 직접 입력** 확인을 요구한다(헌장 P0)
- 리포스트는 건너뛴다(v1 범위). 해제는 M4 `unretweet`
- 타임라인 가상 스크롤이 카드를 언마운트할 수 있다 → 후보가 없으면 스크롤, 그래도 없으면 페이지 새로고침, 그래도 없으면 완료로 판정

## 결과·후속
- SRS FR-18 추가, tasks T34. T33(아카이브 이후 보충)은 이 모드로 흡수
- 아카이브 방식은 그대로 유지한다(필터·dry-run·정확한 진행률이 필요한 경우)
