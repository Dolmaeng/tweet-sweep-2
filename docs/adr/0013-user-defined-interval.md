# ADR-0013: 삭제 간격 사용자 지정 — 간격 하한 폐지

- 상태: 확정 · 2026-09-18 · 사용자 요청("그냥 삭제속도를 내 마음대로 바꿀수있게해줘. 최소 0초과 실수여야하고, 0이하 값을 입력하면 에러를 띄우도록해. 0.3으로 입력하면 삭제주기가 0.3초가 되도록")
- ADR-0008(하드 최소 5초)·ADR-0011(2초→1초)이 정한 **간격 하한을 폐지**한다

## 맥락

간격 하한은 세 번 내려왔다: 10초 → 5초(ADR-0008) → 2초 → 1초(ADR-0011). 매번 "이번엔 여기까지"였고 매번 다시 내려왔다. 사용자는 위험을 알고 있고, 반복해서 더 빠른 속도를 요구했다.

상수를 한 번 더 낮추는 대신 **하한을 없애고 값을 사용자에게 넘긴다**.

## 함정 — 값만 받아서는 0.3초가 되지 않는다

간격을 막고 있던 곳이 둘 더 있었다. 둘 다 고치지 않으면 0.3을 넣어도 아무 일도 안 일어난다.

1. **`Math.max(프리셋 플로어, 사용자 값)`** (`runner.ts`·`sweep.ts`). 사용자 값이 프리셋보다 **작으면 버려진다**. 신중(30초)에 0.3을 넣으면 30초로 달린다
2. **예산 분산 산식 `W ÷ (u·L)`**. 보통 프리셋은 실측 예산에서 약 6.4초를 강제한다. 플로어만 낮춰도 `Math.max`에 걸려 그대로다 — ADR-0011이 이미 겪은 함정인데, 그때는 `burst` 플래그로 `rush`만 빠져나갔다

그래서 `withCustomInterval(preset, sec)`이 **플로어를 갈아끼우면서 `burst`를 함께 켠다**. 분산·워밍업·긴 휴식을 건너뛰고 그 값이 곧 간격이 된다.

## 결정

- `HARD_MIN_DELAY_MS` 삭제. `floorMsOf(preset)`은 이제 프리셋 플로어 그대로다
- `HARD_MIN_FLOOR_SEC` 삭제. 검증은 **0 초과 유한 실수**만 본다
  - `0`·음수 → `삭제 간격은 0보다 커야 합니다`
  - 숫자 아님 → `삭제 간격은 숫자여야 합니다`
  - **상한은 두지 않는다.** 900초를 넣어도 저장된다
- `RunSettings.floorSec`은 "플로어"가 아니라 **"삭제 간격"**이 된다. 값이 있으면 프리셋을 대체한다
- 로그노멀 지터는 유지한다. 정확히 0.300초 반복은 가장 탐지하기 쉬운 패턴이고, 평균 비용은 +6%뿐이다
- 프리셋은 예산 사용률 `u`만 남긴다. **속도만 바꾸지 예산 감시를 푸는 게 아니다**

## 남는 하드 제약

| 제약 | 상태 | 이유 |
|---|---|---|
| 간격 하한 | **폐지** | 사용자가 정지 위험을 알고 직접 정한다 |
| `HARD_MAX_UTIL` 0.95 | 유지 | 잔여 5%를 남겨 429를 정통으로 맞지 않는다. 이게 풀리면 사다리 3회로 다음 날까지 정지라 오히려 느려진다 |
| `HARD_MAX_PER_DAY` 8,000 | 유지 | 헤더 오독 대비 안전망(ADR-0008) |
| 회로차단·활동 시간대·예산 감시 | 유지 | 속도와 무관한 사고 방지 장치다 |

간격은 사용자가 정하지만 **창 예산이 여전히 실질 상한**이다. 0.3초로 달리면 실측 L=200/15min 창을 약 57초 만에 비우고 나머지 843초를 리셋 대기로 보낸다. 하루 총량은 1초일 때와 같다 — 빨라지는 건 한 묶음 안에서다.

## 예상치 정직성

`estimate()`가 폭주 모드에서 창 예산만 세고 있었다. 사용자 지정 간격이 **느릴** 수도 있게 되면서 그게 틀린 계산이 됐다(300초 간격을 140건/창으로 세면 47배 과대평가). 이제 창 예산과 간격 **둘 다의 최솟값**을 쓴다.

계획 화면의 예상 소요도 프리셋이 아니라 사용자 지정 간격으로 센다. 안 그러면 설정과 화면이 다른 말을 한다.

## 위험

- **1초 미만은 사람으로 보이지 않는다.** 워밍업도 긴 휴식도 없다. 설정 화면에서 1초 미만을 입력하면 그 문장을 배너로 띄운다
- 창 예산을 빠르게 소진할수록 429·잠금 판정에 자주 노출된다. 회로차단은 그대로 작동하지만 잠금 자체를 막지는 못한다
- 잠금 시 대응: 간격을 비우고(프리셋으로 복귀) 재개
- 라이브 검증 대기: 1초 미만에서 실제 429 발생 시점, 잠금 여부

## 대안

| 대안 | 내용 | 판단 |
|---|---|---|
| 하한을 0.1초로 한 번 더 낮추기 | 상수 하나 | 기각: 같은 요청이 네 번째다. 숫자를 또 고르는 대신 결정을 넘긴다 |
| 사용자 값을 플로어로만 쓰기 | 기존 구조 유지 | 기각: 분산 산식과 `Math.max`에 걸려 0.3초가 되지 않는다. 요청을 만족하지 못한다 |
| `HARD_MAX_UTIL`도 풀기 | 완전 무제한 | 기각: 요청 범위 밖이고, 429를 정통으로 맞으면 오히려 느려진다 |
| 상한(예: 1시간) 두기 | 오입력 방어 | 기각: 요청은 "0 초과"다. 느린 값은 위험하지 않고, 배너가 무슨 일이 일어날지 말해준다 |
