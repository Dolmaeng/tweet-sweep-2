# ADR-0014: 읽기 한도 관측과 페이지 단위 장애 — 멈추지 말고 물러나기

- 상태: 확정 · 2026-09-19 · 사용자 보고("항상 200개 삭제쯤 가까워지면 `error (page:unknown)`이 난다")
- ADR-0007(적응형 페이싱)의 예산 관측 범위를 넓히고, 실패의 종류를 가른다

## 증상과 원인

`page:unknown`은 `detectPageKind`가 **글도 없고 "삭제된 글" 표시도 없는 화면**을 만났다는 뜻이다. 예산이 바닥난 뒤 X가 내보내는 `Something went wrong. Try reloading.` 화면이 여기 해당한다. 글의 문제가 아니라 **페이지가 안 열린 것**이다.

하필 200쯤인 이유: 실측 DeleteTweet 한도가 200건/15분이다(ADR-0008). 게다가 아카이브 모드는 **1건 삭제 = 1페이지 로드**라 읽기 요청이 삭제와 1:1로 늘어난다. 사용자 지정 간격 0.3초(ADR-0013)면 약 1분 만에 창 예산에 닿으므로, 매번 같은 지점에서 벽에 부딪힌다.

막지 못한 이유는 두 겹이다.

1. **관측 범위가 삭제뿐이었다.** `background.ts`가 `isGraphqlDelete`로 걸러 DeleteTweet 응답만 읽었다. 읽기(TweetDetail·UserTweetsAndReplies)의 한도 버킷은 아무도 보지 않았다.
2. **관측 전에는 감시가 통째로 무력하다.** `scheduler.ts`의 `if (snap.remaining !== null && shouldWaitForReset(...))` — `remaining`이 `null`이면 조건 전체가 건너뛰어진다.

여기에 2026-09-19의 "연속 오류 자동 중지 폐지"가 겹치면 더 나빠진다. 200에서 막힌 뒤 멈추지 않고 남은 글을 간격마다 훑으며 전부 `failed`로 소진한다. 자는 동안 돌리면 아침에 대부분이 실패로 찍혀 있다.

## 결정

### 1. 모든 GraphQL 연산의 예산을 관측한다

`graphqlOperation(url)`로 연산명을 뽑아 `BUDGET`/`RATE_LIMIT` 이벤트에 실어 보낸다. 대시보드는 연산별 버킷을 들고 있다가 **남은 비율이 가장 낮은 버킷**을 실행 판단에 쓴다(`core/budget-buckets.ts`).

절대 수치가 아니라 비율로 고르는 이유: 한도가 다른 버킷끼리는 잔여 수치를 직접 비교할 수 없다. 읽기 50 중 5(10%)가 삭제 200 중 60(30%)보다 먼저 바닥난다.

버킷은 `resetSec`이 지나거나 15분이 넘으면 버린다. 이미 리셋된 창의 값으로 판단하면 안 된다.

### 2. 페이지 단위 실패를 글 단위 실패와 가른다

`Signal`에 `page_unavailable`을 더하고, `detectPageKind`가 글 화면이 아니라고 할 때 이 신호를 낸다. 종래에는 `dom_changed`였는데, 그건 "셀렉터가 바뀌었다"는 뜻이라 원인이 전혀 다르다.

`isPageLevelSignal()`은 `page_unavailable`과 `unknown_error`(탐색·탭 예외)를 페이지 단위로 본다. `dom_changed`는 그 글에서 실제로 벌어진 일이므로 포함하지 않는다.

### 3. 페이지 단위 실패는 그 글의 재시도 횟수를 깎지 않는다

`markItem`·`upsertJobItem`에 `countAttempt` 인자를 더했다. 서버가 막아서 못 연 것으로 `attempts`가 3에 닿으면, 멀쩡한 글이 영영 제외된다(`requeueFailed`가 상한을 보기 때문).

스윕도 같다. 페이지 단위 실패는 `skip`에 넣지 않는다 — 아래 백오프로 물러났다가 같은 글을 다시 집는다.

### 4. 멈추지 않고 물러난다

연속 페이지 장애마다 1분 → 2분 → 5분 → 15분(창 하나)으로 기다렸다가 계속한다(`core/backoff.ts`). 중지가 아니므로 밤새 도는 목표는 그대로다. `pageBackoffMs`는 절대 0을 주지 않는다 — 0이면 장애 중에 큐를 태운다.

스윕에는 하나 더 있다. 새로고침해도 페이지가 글 화면이 아니면 **"더 지울 글이 없음"으로 읽지 않는다.** 그대로 두면 예산이 바닥난 순간 작업이 조용히 "완료"로 끝난다.

## 남는 것

- 예산 표시에 발목을 잡는 연산명을 함께 띄운다: `X 예산(TweetDetail): 한도 50, 잔여 3`
- 관측 전 문구를 고쳤다. "첫 삭제 후 갱신됩니다"는 안심시키는 말이었는데, 실제로는 **그동안 한도 감시가 없다**는 뜻이다
- 라이브 검증 대기: 읽기 버킷의 실제 한도값, 백오프 뒤 실제로 복구되는지

## 대안

| 대안 | 내용 | 판단 |
|---|---|---|
| 관측 전에는 보수적 기본값으로 대기 | `remaining`이 null이면 가정 한도로 판단 | 보류: 지금은 모든 연산을 관측하므로 첫 요청 뒤 바로 값이 생긴다. 그래도 안 오면 별도 결정 |
| `page:unknown`에서 중지 | 원래대로 | 기각: 사용자가 밤새 무인 실행을 요구했다. 중지는 목표와 정면으로 충돌한다 |
| 재시도 없이 그 글을 버리기 | 단순 | 기각: 서버 장애로 멀쩡한 글을 잃는다 |
| 간격을 자동으로 늦추기 | 장애 시 속도 하향 | 보류: 사용자가 간격을 직접 정하기로 했다(ADR-0013). 임의로 바꾸면 그 결정을 뒤집는다 |
