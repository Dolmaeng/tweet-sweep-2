# ADR-0012: 보존 필터 통합과 능력 매트릭스

- 상태: 확정 · 2026-09-18 · 사용자 보고("'분석 → 삭제 실행'에는 필터링 옵션이 없다. UI가 헷갈린다")
- FR-04(아카이브 필터)와 FR-18a(스윕 보존 필터)를 하나로 합친다. 설계 근거는 docs/spec/04-screens.md

## 맥락

사용자가 아카이브 경로로 삭제를 돌렸고 **미디어가 지워졌다**. 그 경로에는 미디어를 남길 방법이 없었다.

`Post.hasMedia`·`mediaTypes`는 이미 아카이브에서 읽고 있었고 분석 화면도 "미디어 포함" 건수를 보여주고 있었다. 데이터는 있는데 `FilterSpec`에 규칙만 없었다. 즉 기능 부족이 아니라 **두 화면이 따로 자라서 생긴 틈**이다.

같은 뿌리에서 세 가지가 나왔다.

1. 아카이브 삭제의 유일한 입구가 `분석`이었다 — 리포트 이름이라 삭제하러 가는 길인 줄 모른다
2. 두 모드의 필터가 어휘도 방향도 달랐다(`대상 조건`/포함 vs `트윗 청소기 필터`/제외)
3. 없는 조건이 **화면에서 그냥 사라져 있었다**. 사용자는 "체크 안 함"과 구별할 수 없다

## 결정

### 1. `core/keep-filter.ts` 하나로 합친다

`filters.ts`(`FilterSpec`)와 `sweep-filter.ts`(`SweepFilter`)를 지우고 `KeepFilter` 하나를 두 모드가 읽는다. 판정 함수만 둘이다(`isTargetArchive` / `isKeptSweep`).

섞여 있던 방향은 **섹션으로 가른다**. §무엇을 지울까는 포함(멘션·종류·기간·포함 키워드), §지우지 않을 글은 보존(미디어·지표·글 ID·제외 키워드). 한쪽으로 통일하지 않은 이유는 "이 말이 든 글만 지우기"가 실제로 쓸모 있는 조건이라 버릴 수 없어서다. 섹션 제목이 방향을 말하면 섞이지 않는다.

### 2. 능력 매트릭스가 UI와 판정을 동시에 지배한다

`CAPABLE_FLAGS`·`CAPABLE_FIELDS`가 모드별로 쓸 수 있는 조건을 정의하고, **화면 잠금과 판정 경계가 같은 표를 본다**. 이러면 구조적으로 불가능해지는 것이 두 가지다.

- 화면에 보이는데 판정에서 무시되는 조건
- 안 보이는데 적용되는 조건

이번 사고는 전자의 극단(아예 안 보임)이었다. 표가 하나면 둘 다 안 생긴다.

### 3. 못 하는 조건은 숨기지 않고 잠근다

비활성 줄 + 왜 못 하는지 한 줄(`아카이브에서 like.js를 읽지 않습니다` 등). 헌장 P0(정직)의 UI판이다. **되돌릴 수 없는 작업에서 "없다"와 "안 골랐다"가 같아 보이면 안 된다.**

정밀도가 낮은 경우는 잠그지 않고 문구로 밝힌다: 스윕의 좋아요 조건은 숫자 입력 대신 "1개 이상" 고정이다.

### 4. 시작 직전 되읽기

`KeepRecap`이 "N건을 지웁니다 / 남깁니다: …"를 문장으로 보여준다. `keepReasons()`가 그 모드에서 **실제로 적용되는** 조건만 뽑으므로, 되읽기에 안 나오는 조건은 적용되지도 않는다. 남기는 조건이 없으면 "전부 지웁니다"를 붉게 띄운다.

### 5. 입구를 대칭으로

홈에 `[아카이브로 삭제]`와 `[아카이브 없이 삭제]`를 같은 무게로 나란히. `분석`은 리포트로 되돌리되 `[이 아카이브로 삭제 →]` 링크는 남긴다(이름이 모드를 말한다).

## 능력 매트릭스 (요약)

| 조건 | 아카이브 | 스윕 |
|---|---|---|
| 멘션 구분 · 제외 키워드 | ✅ | ✅ |
| 미디어가 있는 글 | ✅ (**신규**) | ✅ |
| 내가 올린 미디어만 | 🔒 인용 구분 불가 | ✅ |
| 내가 좋아요·북마크·리포스트한 글 | 🔒 아카이브에 없음 | ✅ |
| 좋아요·리포스트 N개 이상 | ✅ 정확 | ⚠️ "1개 이상"만 |
| 기간 · 종류 · 포함 키워드/정규식 · 글 ID | ✅ | 🔒 |

전체 표는 docs/spec/04-screens.md §5.

## 대안

| 대안 | 내용 | 판단 |
|---|---|---|
| 아카이브에 미디어 조건만 추가 | 상수 하나, 체크박스 하나 | 1단계로 먼저 넣었다. 하지만 어휘가 두 벌인 채라 다음 조건에서 같은 틈이 다시 생긴다 |
| 모드를 하나로 합치기 | 아카이브 유무를 내부에서 판단 | 기각: 읽는 재료가 근본적으로 다르다. 합치면 "왜 이 조건이 안 되는지"를 설명할 자리가 사라진다 |
| 못 쓰는 조건을 숨기기 | 화면이 깔끔해진다 | **기각. 이번 사고의 원인이 정확히 그것이다** |
| 필터를 한 방향(보존)으로만 | 어휘가 더 단순 | 기각: "이 말이 든 글만 지우기"를 표현할 수 없다. 섹션으로 가르는 편이 손실이 없다 |

## 위험·후속

- 저장값 마이그레이션: `coerceKeepFilter()`가 구버전 `SweepFilter`(`exclude[]`·`keywords`)를 읽어 옮긴다. 플래그 이름이 같아 변환이 단순하다. 실패는 "필터 없음"이 아니라 **오류**로 처리한다(664e9e5 가드와 같은 이유)
- `job.filterSpec`은 `unknown`으로 저장돼 스키마 변경에 영향 없다. 이어서 하기는 화면의 현재 필터를 쓴다
- 아카이브 필터도 이제 저장한다(`archiveFilter` 키). 매번 다시 체크하지 않게
- 종류를 둘 다 끄면 대상 0이다. 기본값으로 되돌리면 안 끄느니만 못하다
- 라이브 검증 대기: 실제 아카이브에서 `hasMedia` 분포, 잠금 UI가 실제로 읽히는지
