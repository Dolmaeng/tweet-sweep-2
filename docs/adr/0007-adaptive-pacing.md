# ADR-0007: 적응형 페이싱 — 관측한 rate-limit 예산의 일부만 사용, 고정 간격 대신

- 상태: 확정 · 2026-09-17 · SRS §6 v0.3 근거. 사용자 요청(brisk 10~13s, 일일 상한 폐지)과 외부 "탐지 회피 가이드" 검토 반영

## 맥락
- 사용자: brisk 25~35s·일 1,500건은 너무 느림. 10~13s 간격 요청. 외부 가이드(0.6s 하한, 시간당 1,000~1,500건, UA·IP 회전, 주간 재로그인, 위장 활동 등) 제시
- 사실: 공식 API 삭제 한도 50/15min. 웹 클라이언트 한도는 비공개지만 응답마다 `x-rate-limit-*` 헤더로 예산이 드러남(Cyd 관측). 반복 429는 X가 명시한 잠금 사유("자동화 의심")

## 결정
- 간격을 고정하지 않고 관측된 예산(L, W)의 사용률 u로 산출: 간격 = W ÷ (u·L). 프리셋은 u와 플로어만 다름. brisk u=0.7, 플로어 10s
- 잔여(R) 감시로 429 이전에 멈춤. 429 발생 시 사다리식 감속. 헤더 미관측 시 L=50 가정·u=0.3 고정
- 지터는 로그노멀 + 간헐적 긴 휴식. 활동 시간대 시작·종료 무작위
- 일일 고정 상한 폐지 → 예산 파생값 ±15%. 절대 상한 5,000/일

## 이유
- 속도의 진짜 상한은 X의 예산이지 우리 추측이 아니다. 헤더를 읽으면 "가능한 만큼 빠르게"를 근거 있게 달성하고, 429를 반복해 잠금 신호를 만드는 일을 피한다
- 10~13s 고정은 양날: L=50이면 약 7분마다 429(위험 상승), L≥130이면 필요 이상으로 느림. 적응형은 두 경우 모두 맞는 속도로 수렴
- 로그노멀: 사람의 행동 간격은 오른쪽 꼬리가 긴 분포. 정규분포를 하한으로 잘라내면 하한에 봉우리가 생겨 오히려 기계적

## 외부 가이드 항목별 판단
| 항목 | 판단 | 이유 |
|---|---|---|
| 하한 0.6s, 시간당 1,000~1,500건 | 기각 | 공식 삭제 한도의 5~7배. Tweet-Removal-Tool이 600ms에서 429 발생 인정 |
| 가우스 지터 | 부분 채택 | 비균등 지터는 타당. 분포는 로그노멀로 교체 |
| 간헐적 긴 휴식, 시각 무작위 | 채택 | 비용 없이 규칙성 제거 |
| 429 시 장기 대기·에스컬레이션 | 채택(수정) | 사다리식 + 잔여 감시로 선제 |
| 단일 동시 요청, 상태기계, 진행 대시보드 | 채택 | 기존 설계와 동일 |
| User-Agent 회전 | 기각 | 같은 세션·쿠키·기기에서 UA만 바뀌면 불일치 신호. 확장은 페이지 요청의 UA를 바꾸지 못하고, UI 클릭 실행기는 헤더에 손대지 않음 |
| IP·프록시 회전 | 기각 | 한 계정이 여러 IP에서 접속 = 계정 탈취 신호 → 즉시 잠금·비밀번호 재설정 |
| 주 1회 로그아웃·재로그인 | 기각 | 로그인 이벤트가 위험 신호·2FA 유발. 세션 유지가 더 자연스러움 |
| 자동 좋아요·게시 위장 | 기각 | 자동 참여는 X가 가장 강하게 단속하는 행위. 삭제보다 위험 |
| 백그라운드 워커가 "더 자연스러움" | 기각 | 실행 위치는 요청 특성과 무관. MV3 워커는 장기 루프 불가(ADR-0004) |
| 구글 시트 로그 | 기각 | P2(외부 전송 0) 위반 |
| "15분당 300 요청" | 사실 오류 | 공식 삭제 한도는 50/15min |

## 결과·후속
- SRS §6 v0.3, plan §5 개정. M2 스파이크에서 DeleteTweet 응답의 L·W 실측 → 프리셋 표의 실제 간격 확정
- 측정된 L이 커서 UI 클릭 플로어(≈8~10s)보다 빠른 속도가 가능하고 사용자가 원하면 `graphql-replay` 전환 검토(ADR-0005 단서)
