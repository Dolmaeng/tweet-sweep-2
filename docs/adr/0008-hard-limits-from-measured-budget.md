# ADR-0008: 하드 제약 재설정 — 실측 예산(L=200/15min) 기준 간격 ≥5s·일 ≤8,000

- 상태: 확정 · 2026-09-17 · ADR-0007 수치 개정. 사용자 확인 후 채택

## 맥락
- 사용자 요구: 10시간 실행에 30,000건. 기존 하드 최소 10s로는 10시간 3,600건(26,780건에 약 7.5일)
- 실측(T14·M3): 웹 클라이언트 DeleteTweet `x-rate-limit-limit`=200, 창 15분 → X 예산 상한 4.5s/건, 10시간 8,000건. 30,000/10h는 예산의 3.75배라 어떤 방식으로도 불가(4분마다 429)
- 기존 10s 플로어는 L 실측 전 보수값. L=200에서는 산식값(W÷(u·L)=6.4s)보다 플로어가 커서 적응형이 무의미했음

## 결정
- `HARD_MIN_DELAY_MS` 10,000 → 5,000. brisk 플로어 10s → 5s. `HARD_MAX_UTIL` 0.7 유지 → brisk 실효 간격 ≈6.4s(워밍업 첫 100건 u=0.3 ≈15s → 300건까지 선형 상승)
- `HARD_MAX_PER_DAY` 5,000 → 8,000 (u=0.7·L=200·24h = 13,440의 안전 절반 수준, 24h 실행 시 상한 역할)
- 간격 정의를 '삭제 시작 시각 간 간격(cadence)'으로 명확화. 탐색·클릭 소요는 차감(커밋 d5d0475)

## 대안
| 선택지 | 간격 | 10h | 26,780건 | 429 위험 | 판단 |
|---|---|---|---|---|---|
| 유지(10s) | 10s | 3,600 | ≈7.5일 | 낮음 | 사용자 거부 |
| **A. 최소 5s·u 0.7** | 6.4s | 5,600 | ≈5일 | 낮음(30% 여유) | **채택** |
| B. 최소 4.5s·u 0.9 | 5s | 7,200 | ≈4일 | 중간(창 끝마다 잔여 대기) | 기각: 사용자 수동 활동 여유 없음 |
| 예산 초과 | <4.5s | — | — | 확실한 429·잠금 | 기각 |

## 이유
- 30% 여유(u=0.7)는 사용자가 같은 세션에서 수동으로 글을 지우거나 X가 창 경계를 다르게 계산해도 429를 맞지 않는 완충. 잔여 감시(R<(1−u)L → 대기)와 함께 429 0회를 목표
- 하드 최소를 4.5s가 아닌 5s로 둔 것은 UI 클릭 실행기의 탐색·렌더 소요(3~5s) 아래로 내려가면 의미가 없고, 헤더 미관측(L=50 가정) 상황에서의 안전 여유도 남기기 위함

## 결과·후속
- SRS §6·§9·Q6, plan §5 수치 개정. 설정 화면 하드 제약 문구는 상수에서 읽으므로 자동 반영
- 실측 창 길이가 900s가 아니면(리셋 헤더로 확인) 산식이 자동 보정. 429가 1회라도 나오면 브레이커 사다리(ADR-0007) 그대로
